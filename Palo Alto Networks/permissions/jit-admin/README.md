# PAN-OS – JIT Administrator

Creates a temporary local administrator on a firewall or Panorama at checkout, commits only the broker's own change, returns the credential, and deletes the administrator at checkin. Between checkouts the account does not exist.

| Script | Purpose |
|---|---|
| `checkout.py` | `edit` `mgt-config/users/entry[@name='brt-<user>']` with a device-generated `phash` and the requested role; `commit partial`; verify |
| `checkin.py` | `delete` the entry; `commit partial`; verify; log out any session the account still holds; retry once |
| `panos_api.py` | Shared XML API helper (imported by both and by `../../rotate/`) — keep it here |

## Roles

`PANOS_ROLE` selects the permission block written to the administrator:

| Value | Result | Use for |
|---|---|---|
| `superreader` (default) | `<superreader>yes</superreader>` | Read-only firewall/Panorama access |
| `superuser` | `<superuser>yes</superuser>` | Full admin |
| `panorama-admin` | `<panorama-admin>yes</panorama-admin>` | Panorama administration |
| `custom:<profile>` | `<custom><profile>NAME</profile></custom>` | Any Admin Role profile you have defined (*Device > Admin Roles*), e.g. `custom:netops-objects-only` |

Create one Britive profile per role; the permission is the same, only the variable differs. `custom:` profiles are where least privilege lives: an Admin Role profile can restrict tabs, enable XML API only, or allow commit without config changes.

## Environment variables

| Variable | Required | Description |
|---|---|---|
| `PANOS_HOST` | Yes | Firewall or Panorama management address |
| `PANOS_API_USER` | Yes | Broker's administrator |
| `PANOS_API_PASSWORD` or `PANOS_API_KEY` | Yes | Secrets Store |
| `BRITIVE_USER_EMAIL` | Yes | Requesting identity |
| `PANOS_ROLE` | No | See above; default `superreader` |
| `PANOS_JIT_PREFIX` | No | Default `brt-`; `""` disables and an existing admin then makes the checkout refuse |
| `PANOS_PASSWORD_LENGTH` | No | Default `20` (upper, lower and digit guaranteed) |
| `PANOS_CHECKIN_RETRIES` | No | checkin only; default `1` |
| `PANOS_COMMIT_TIMEOUT` | No | Seconds to wait for the commit job; default `300` |
| `PANOS_PORT`, `PANOS_VERIFY_TLS`, `PANOS_CA_BUNDLE` | No | Connection options |

## Output

```json
{"login":"brt-alice","hostname":"fw-edge-01","password":"…","role":"superreader","web_url":"https://fw-edge-01/","ssh_command":"ssh brt-alice@fw-edge-01"}
```

Checkin prints nothing.

## Britive Broker Config Example

```yaml
resource_types:
  panos:
    jit-admin:
      max_supported_version: local
      execution_environment: python3 <BRITIVE_PERMISSION_SCRIPT>
      checkout_script: /opt/britive-broker/scripts/Palo Alto Networks/permissions/jit-admin/checkout.py
      checkin_script:  /opt/britive-broker/scripts/Palo Alto Networks/permissions/jit-admin/checkin.py
```

`PANOS_HOST` from the resource, `PANOS_ROLE` from the permission variable, the API credential from the Secrets Store.

## Behavior notes

- A leftover `brt-<user>` from a failed checkin is refreshed in place (`edit` replaces the whole entry, so the role is reset to the profile's value). With `PANOS_JIT_PREFIX=""`, an existing administrator makes the checkout refuse rather than overwrite it.
- The password hash is generated by the device (`request password-hash`), so it matches the device's algorithm and the plaintext never appears in the candidate config.
- `commit partial admin <broker>` commits only objects the broker changed. If another administrator holds a **commit lock**, the commit fails and so does the checkout; release the lock or exclude the broker from locking policy.
- After deletion, checkin issues `request logout admin <user>` so an open web session for the deleted account is terminated.
- Session recording and a credential the user never sees: front the firewall's SSH and web UI with Britive Bridge and feed it the checkout result instead of returning it to the user.
